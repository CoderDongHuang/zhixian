# 知线项目现状审计与演进建议

审计日期：2026-08-23

复核更新：2026-08-24

审计对象：`main` 分支当前代码、工作区未提交移动端改动、现有设计/发布文档、GitHub Actions 运行状态

项目版本：根项目 `0.4.0-rc.1`，移动端 `0.4.0`

## 1. 结论摘要

知线已经从最初的 Web/PWA 验证版扩展为包含 Web、React Native App、微信小程序、内容采集、AI 分析、实体关系、学习路线、邮件和推送的多端产品。核心业务骨架完整，单元测试覆盖了推送、回执、学习、微信同步、实体合并、小程序和发布准备检查。

审计时的工作区不适合直接继续发布移动端或恢复全量自动化，主要原因如下：

1. 当前未提交的移动端改动无法通过 TypeScript 检查，且新增 Sentry 配置会默认采集个人信息，与现有隐私说明冲突。
2. GitHub Actions 因账户的 Actions 月预算为 `$0` 且启用停止使用而无法启动；目前四个定时工作流已按需求手动停用，因此内容、摘要、监控和推送回执不会自动更新。
3. OTP 验证端缺少失败次数/IP 级限流，登录接口存在验证码暴力尝试、邮箱轰炸和账号枚举风险。
4. 多个批处理脚本会记录失败但仍以退出码 0 结束，可能出现“流水线绿色、实际没有产出”的假成功。
5. 采集逻辑按 URL 直接跳过已存在内容，GitHub 仓库、公告和持续更新页面不会刷新，长期会形成陈旧数据。
6. 当前依赖审计发现 13 个高危、15 个中危项，仓库内 2026-08-02 的依赖审计结论已经过期。
7. 生产数据库仍依赖 `prisma db push` 和零散 SQL 升级脚本，缺少可追踪、可回滚的正式迁移链。

建议先完成一轮“稳定性与安全性版本”，再继续增加趋势监测、问答或企业功能。

## 4. 当前问题与 Bug

### P0：立即阻塞发布

#### P0-1 当前移动端工作区无法通过类型检查

**证据**

- `mobile-app/app/_layout.tsx:9` 已从 `src/telemetry` 导入 `Sentry`。
- `mobile-app/app/_layout.tsx:11` 又使用 `import * as Sentry` 声明同名标识符。
- 移动端 TypeScript 检查报 `TS2300 Duplicate identifier 'Sentry'`。

**影响**

- GitHub quality gate 和 EAS 发布检查会失败。
- 两处 `Sentry.init` 造成初始化职责重复，配置结果不可预测。

**建议**

- 保留 `src/telemetry.ts` 作为唯一 Sentry 初始化入口。
- 根布局只导入封装后的 `Sentry` 和 `track`。
- 增加测试，确保 Sentry 仅初始化一次。

#### P0-2 未提交的 Sentry 配置造成隐私回归

**证据**

- `mobile-app/app/_layout.tsx:18` 设置 `sendDefaultPii: true`。
- `mobile-app/src/telemetry.ts` 原配置为 `sendDefaultPii: false`。
- App 设置页声明“不发送邮箱、阅读正文或设备标识；崩溃报告默认移除个人信息”。
- 新配置还开启 Session Replay，且错误回放采样率为 100%。

**影响**

- 实际采集行为与隐私政策、界面承诺不一致。
- 可能采集账号、页面内容、输入或设备上下文，带来合规和应用商店审核风险。

**建议**

- 禁止默认 PII，Session Replay 默认关闭。
- 若未来启用回放，必须先完成字段脱敏、用户明确同意、隐私政策更新和数据保留规则。
- DSN 使用 `EXPO_PUBLIC_SENTRY_DSN`，不要在页面代码中硬编码环境配置。

#### P0-3 自动化生产链路当前处于停机状态

**证据**

- Actions 预算为 `$0` 且 `Stop usage = Yes`。
- GitHub 拒绝启动任务，并提示付款或消费额度问题。
- 四个定时工作流已手动停用。

**影响**

- 信息流不会获得新内容。
- 邮件、关键词提醒和移动推送不会自动投递。
- 线上故障不会由该监控工作流发现。
- Expo 推送回执不会更新，失效设备不会自动清理。

**建议**

- 如果项目暂时停止运营，保持停用并在 README 顶部标记“自动化暂停”。
- 恢复运营前添加有效付款方式或迁移调度平台，然后逐个启用并验证，不要一次性全部开启。
- 启用顺序：数据库迁移 -> Content pipeline -> Digest delivery -> Push receipts -> Production monitor。

### P1：高优先级安全与正确性问题（以下为初次发现，修复结果见上表）

#### P1-1 OTP 登录缺少验证失败限流和锁定

**证据**

- `app/api/auth/request-code/route.ts` 仅按邮箱限制 60 秒内重复发送。
- `app/api/auth/verify-code/route.ts` 和 `app/api/mobile/auth/verify-code/route.ts` 没有 IP、设备、邮箱失败次数或验证码尝试上限。
- 验证码为 6 位，有效期 10 分钟。
- 请求验证码时，新用户无有效邀请码返回 403，已有用户进入发送流程，响应差异可用于账号枚举。

**影响**

- 攻击者可以高速尝试验证码。
- 可利用接口向已注册邮箱反复发送邮件。
- 可以判断某邮箱是否已经注册。

**建议**

- 引入 Redis/Upstash 等共享限流：IP、邮箱和设备三个维度。
- 单个 OTP 最多允许 5 次失败，超限立即作废。
- 增加每小时、每天发送上限和渐进退避。
- 对外统一响应文案和耗时，避免账号枚举。
- 记录安全事件，但不要记录验证码或令牌。

#### P1-2 批处理失败会被误报为成功

**证据**

- `ingest-sources.mjs`、`ingest-community.mjs` 捕获每个来源错误后只打印日志。
- `process-documents.mjs`、`analyze-events.mjs`、`extract-entities.mjs` 统计 `failed`，但结束时没有设置非零退出码。
- `send-digests.mjs` 即使所有邮件发送失败，也只写数据库和输出汇总。
- `send-keyword-alerts.mjs` 对 Resend 非 2xx 结果写失败记录，但不会使进程失败。
- `send-push.mjs` 可以产生大量 `failed`，仍正常退出。

**影响**

- CI/调度平台显示成功，但内容、邮件或推送实际失败。
- 失败告警步骤不会触发，形成长期静默故障。

**建议**

- 定义批处理退出策略：系统级错误立即失败；失败率超过阈值时退出 1；允许的单来源降级退出 0 但输出 warning。
- 输出统一结构化运行摘要并保存 `JobRun`/`PipelineRun` 记录。
- 对“0 条输入”“0 条产出”“全部投递失败”分别设告警。

#### P1-3 已存在 URL 永远不会更新

**证据**

- `scripts/ingest-sources.mjs:59` 在 URL 或 `contentHash` 已存在时直接 `continue`。
- `RawDocument.url` 为唯一键。
- GitHub 仓库 URL、官方公告页面和社区帖子可能在原 URL 上持续更新。

**影响**

- GitHub Stars、Forks、描述和更新时间只保留首次采集值。
- 更正后的公告、持续更新页面不会刷新。
- 趋势分析基于陈旧快照，无法支持未来的时间序列功能。

**建议**

- 区分“不可变文章”和“可变实体/项目快照”。
- 对可变来源使用 upsert，并保存 `SourceSnapshot` 历史表。
- `contentHash` 应基于规范化正文，而不是仅 `url:title`。
- 为 ETag、Last-Modified 和抓取版本增加字段。

#### P1-4 聚类与发布规则可能导致大量内容无法发布

**证据**

- `createClusterKey` 只对标题分词、去停用词、排序后哈希，并不是真正的语义聚类。
- 排序 token 会丢失词序，“A 收购 B”和“B 收购 A”可能得到相同键。
- 不同媒体标题略有变化时，又可能无法合并成同一事件。
- `analyze-events.mjs:39` 将单来源事件置信度上限设为 `0.74`。
- 自动发布阈值为 `0.78`，所以单来源事件第一次分析必定进入审核。
- `auto-resolve-reviews.mjs` 可能二次自动发布，但当前 Content pipeline 没有运行 `reviews:auto-resolve`。

**影响**

- 事件可能错误合并或重复出现。
- 大量单来源事件停留在待审核，信息流产出不稳定。
- 架构文档宣称的“事件聚类、多来源验证、低置信度复审”与实际调度不完全一致。

**建议**

- 采用“两阶段聚类”：时间窗口/实体候选召回 + embedding/LLM 判定。
- 保留聚类理由、相似度、人工拆分和合并记录。
- 明确单来源官方公告的发布策略，不应简单等同于低可信内容。
- 将自动复审加入明确队列，或从文档中删除“自动复审已运行”的暗示。

#### P1-5 依赖安全审计结论已经失效

**证据**

- 2026-08-23 的 `npm audit --omit=dev`：13 high、15 moderate、0 critical。
- 涉及 Expo/Metro、Prisma/deepmerge-ts、fast-uri、image-size、nanoid、PostCSS 等。
- `docs/security/dependency-audit-v0.4.md` 仍写“无 high/critical”。

**影响**

- 发布门禁依据过期文档做出错误判断。
- Expo/Metro 多项问题需要 SDK 大版本升级，不能只靠零散 override 长期维持。

**建议**

- 先处理可无破坏升级的 Prisma、fast-uri、nanoid、PostCSS。
- 单独建立 Expo SDK 54 -> 57 升级分支，完成原生模块、Router、Updates、Notifications 和 EAS 真机回归。
- 在 CI 中执行机器可读审计，并对新增 high/critical 阻断。
- 安全审计文档必须记录 lockfile commit，而不是只记录日期。

#### P1-6 生产数据库没有正式迁移链

**证据**

- 生产工作流执行 `prisma db push`。
- 仓库同时保留多个 `upgrade-*.sql`，但没有 Prisma migrations 历史目录。
- 发布手册要求“先部署 schema”，但缺少回滚 SQL、备份校验和迁移状态表。

**影响**

- 无法可靠审计某环境执行过哪些变更。
- 破坏性 schema 变化难以预演和回滚。
- 多环境容易发生 drift。

**建议**

- 迁移到 `prisma migrate deploy` 或受控 SQL migration 工具。
- 每次迁移必须包含前置检查、备份点、向后兼容窗口和回滚说明。
- 禁止生产直接使用 `db push`。

### P2：中优先级工程与体验问题（以下为初次发现，修复结果见上表）

#### P2-1 退订通过 GET 修改状态，且令牌永久有效

- `app/unsubscribe/page.tsx:10` 在 `confirmed=1` 的 GET 请求中直接关闭邮件。
- 邮件安全扫描器、浏览器预取或代理访问链接时可能误触发退订。
- token 只由 `AUTH_SECRET + userId` 生成，没有到期时间和用途版本，泄露后可长期复用。

建议改为 GET 展示确认页、POST 执行退订；token 中加入用户、用途、签发时间和过期时间，并支持轮换。

#### P2-2 报告下载通过 GET 写数据库

- `app/api/reports/[id]/export/route.ts:21` 在下载 GET 中创建 `ReportExport`。
- 重试、预取和下载器重复请求会污染统计。

建议把“生成导出任务”改为 POST，再使用只读下载 URL；至少增加幂等键。

#### P2-3 Lint 和根 TypeScript 检查不可用

- `npm run lint` 仍使用已弃用的 `next lint`，且项目没有 ESLint 配置。
- 根 `tsc` 因测试文件 `.ts` 扩展导入和 fetch mock 类型失败。
- quality gate 没有独立执行根 TypeScript 检查和 ESLint。

建议迁移到 ESLint CLI，拆分 `tsconfig.app.json` 与 `tsconfig.test.json`，在 CI 中分别运行 `lint`、Web typecheck、mobile typecheck。

#### P2-4 Embedding 维度配置与数据库类型可能冲突

- `prisma/schema.prisma:656` 固定为 `vector(1024)`。
- `scripts/embed-documents.mjs:7` 允许任意 `EMBEDDING_DIMENSIONS`。

如果环境变量不是 1024，插入会失败。建议启动时强校验维度，或通过迁移统一修改数据库与模型配置。

#### P2-5 移动端同步每次都从 cursor 0 开始

- `mobile-app/src/sync.ts:8` 固定请求 `/api/mini/sync?cursor=0`。
- 服务端会把 cursor 0 当作全量初始同步，并返回全部收藏、阅读、路径和任务快照。

这会在每次重连和后台任务时重复全量读取。建议持久化服务端返回的 cursor，循环处理 `hasMore`，只在首次登录或恢复时请求全量快照。

#### P2-6 移动端网络请求缺少超时和取消

`mobile-app/src/api.ts` 的登录、刷新和业务请求没有 AbortSignal。弱网下 Promise 可能长时间挂起，阻塞同步和界面状态。建议统一封装 10-30 秒超时、可取消请求、错误分类和有限重试。

#### P2-7 监控容易产生性能误报

- 监控把 HTTP 正常和性能阈值合并为一个失败状态。
- 阈值仅 3.5 秒；实测健康和实体页首次请求约 3.0-3.1 秒。
- 两次都超阈值就令整个 workflow 失败并发邮件。

建议将“不可用”和“慢请求”分开；使用多次采样的 P95、连续失败次数和冷启动豁免。性能退化应告警，偶发冷启动不应与宕机同级。

#### P2-8 运行数据缺少清理和保留策略

`EmailOtp`、过期 `Session`、`MiniSession`、`SyncChange`、`SyncRequest`、`BehaviorEvent`、`ReportExport` 和投递记录会持续增长。当前没有定时归档或清理任务。

建议为每类数据定义保留期，并增加每日清理任务、索引监控、表大小指标和隐私删除流程。

#### P2-9 用户行为接口可被自身数据污染

`/api/behavior` 允许客户端直接提交 topic、eventId、feedItemId 和 value，缺少资源归属/存在性校验与请求频率限制。恶意或异常客户端可以写入大量事件、制造 500 或扭曲自己的推荐结果。

建议服务端从 feed/event 查询真实 topic，限制每用户每分钟写入量，并对可重复行为做去重或聚合。

#### P2-10 文档与版本路线发生漂移

- 原路线把“正式 App”列为 V0.3，把“趋势监测”列为 V0.4。
- 当前 Changelog 和 release 文档把 V0.4 定义为原生 App 发布候选。
- README 的“V0.3 移动端”与移动端包版本 `0.4.0` 并存。

建议重建单一版本路线图，明确“已发布、RC、开发中、设想”四种状态，避免用版本号同时表达不同范围。

## 5. 建议优化路线

### 阶段 A：稳定性与安全性修复（1-2 周）

目标：恢复可发布、可检测、不会静默失败的基线。

1. 修复移动端重复 Sentry 初始化，恢复 `sendDefaultPii: false`。
2. 配置 ESLint，修复根/移动端 TypeScript 检查，并纳入 CI。
3. 增加 OTP 发送与验证限流、失败次数和统一响应。
4. 为批处理建立退出码规范和结构化运行摘要。
5. 修复 GET 状态变更：退订和报告导出。
6. 更新可直接修复的高危依赖，建立 Expo SDK 升级分支。
7. 建立自动化暂停/恢复 Runbook。

**验收标准**

- `lint`、Web typecheck、mobile typecheck、unit、E2E 全部非交互通过。
- OTP 暴力尝试和邮件轰炸测试通过。
- 模拟全来源失败时流水线必须退出 1 并产生一次明确告警。
- 隐私说明与 Sentry 实际配置一致。

### 阶段 B：数据质量与任务可靠性（2-4 周）

目标：保证内容真的更新、聚类可解释、失败可重放。

1. 引入 `PipelineRun`、`TaskRun`、`SourceRun` 和失败重试记录。
2. 可变来源使用快照模型，支持 ETag/Last-Modified。
3. 使用候选召回 + 语义判定重做事件聚类。
4. 将采集、处理、分析、实体抽取、摘要生成拆成可重放任务。
5. 对 AI 输出保存 prompt hash、输入文档版本、token/cost、验证结果。
6. 建立人工审核 SLA、抽样准确率和撤回机制。
7. 迁移到正式数据库 migration 链。

**验收标准**

- 任意任务可按 document/event ID 重放且幂等。
- 可查看每次运行输入数、成功数、失败数、成本和耗时。
- 抽样聚类准确率、事实支持率有可追踪基线。

### 阶段 C：性能与可观测性（2-3 周）

目标：把“能运行”提升为“可持续运营”。

1. 监控拆分 availability、latency、freshness、delivery 四类 SLI。
2. 建立内容新鲜度指标：最后成功采集、最后发布、待审核积压。
3. 为数据库慢查询、表增长、连接池和缓存命中率建立仪表盘。
4. 移动端实现增量 cursor 同步、超时和退避。
5. 对公开页面实施按查询热度的缓存和主动失效。
6. 为模型、邮件、推送设置每日成本预算与熔断。

### 阶段 D：产品验证与增长（持续）

目标：先验证用户价值，再扩大功能面。

1. 定义北极星指标：每周有效研究会话数或每周节省研究时间。
2. 跟踪内容打开率、证据展开率、收藏率、纠错率、7/30 日留存。
3. 在增加更多行业前，先验证 AI 行业内容的准确率和复访价值。
4. 用小规模用户访谈校验“信息流、学习、趋势、报告”哪个场景最强。

## 6. 功能扩展建议

### 6.1 优先扩展：可信研究工作台

这是最贴合现有数据和差异化优势的方向。

- 事件订阅：关注公司、模型、项目或技术，而不只是关键词。
- 证据对照视图：结论与原文片段左右对应，展示支持/冲突来源。
- 研究集合：把事件、实体、简报加入专题文件夹并写个人笔记。
- 时间线对比：同一实体 7/30/90 天的重要变化。
- 纠错闭环：用户反馈进入审核队列，修订后通知反馈者。
- 可分享研究页：生成带来源、更新时间和版本号的只读页面。

### 6.2 趋势监测 V0.1

不要一开始做泛化预测，先做可解释指标。

- GitHub：Stars/Forks/Contributors/Release cadence/Issue velocity 快照。
- 模型与产品：发布频率、API 价格、上下文长度、基准变化。
- 论文：主题论文量、引用增长、机构分布。
- 招聘：岗位数、技能关键词、地区和薪资区间（需合法数据源）。
- 趋势卡片展示原始指标、计算方式、时间窗口和数据缺口。
- 预测必须有回测、置信区间和失效条件。

### 6.3 AI 问答与研究代理

- 只基于用户选定专题和可追溯证据回答。
- 回答中的每个事实必须引用文档或事件。
- 支持“比较两个模型/公司/项目”“过去 30 天发生了什么”。
- 异步研究任务可生成大纲、收集证据、等待用户确认后再形成报告。
- 对无证据问题明确拒答或标注推测。

### 6.4 学习功能升级

- 将学习任务与真实事件、实体和先修知识绑定。
- 增加知识检查、错题和间隔复习，而不仅是阅读任务。
- 根据完成质量调整路线，不只根据完成数量计算进度。
- 支持“从行业事件生成 15 分钟实践任务”和代码练习。

### 6.5 团队与企业版

只有在个人版留存稳定后再投入。

- 团队空间、专题、评论、@成员和审批。
- 私有数据源、内部文档 RAG、来源权限隔离。
- RBAC、SSO、审计日志、数据保留策略。
- Webhook/API、定时报表和企业微信/飞书/Slack 投递。
- 企业数据必须与公共数据、模型日志严格隔离。

### 6.6 多行业扩展

先实现行业配置层，再增加行业：

- 来源、术语、实体类型、事件类型、指标、提示词、合规规则全部配置化。
- 每个新行业必须完成来源授权、100-200 条样本评测和人工准确率基线。
- 高风险行业（医疗、金融）必须增加专业审核、免责声明和更严格发布阈值。

## 7. 不建议现在优先做的功能

- 不建议立即拆成大量微服务；当前首要问题是可靠性和治理，不是服务数量。
- 不建议立即支持很多行业；会放大数据质量、审核和来源授权成本。
- 不建议做确定性趋势预测；当前还没有稳定的历史快照和回测数据。
- 不建议先做复杂图谱可视化；应先保证实体去重和关系证据准确。
- 不建议在隐私基线未修复前扩大 Session Replay、行为采集或广告追踪。
- 不建议在质量门禁未恢复前提交 App Store/Google Play 正式审核。
